# `supabase/` — Database schema and seed data

## Contents

- **`migrations/master-migration/LATEST_YYYYMMDD.sql`** — One script that creates the whole schema on an empty database. Generated by **`npm run supabase:master`**, which moves the previous file to **`migrations/master-migration/archive/`**. Standup and `db push` do not apply it.
- **`migrations/feature-migrations/`** — Incremental SQL. Standup applies the paths in **`.lattice/standup.json`** that are new or changed for that database. `deploy:aws` lists new or changed SQL and asks you to type `yes` (`prod` for prod) before terraform runs. Already-applied files are skipped, tracked in `lattice.applied_sql`. Non-interactive runs need `--approve-sql`, and only a person may pass it. Timestamped files directly in **`migrations/`** are symlinks to these, because the CLI does not read subfolders.
- **`migrations/seed/features/`** — Development data. **`npm run supabase:seed`** runs every feature. **`npm run supabase:seed:things`** runs the Thing demo rows.

## Rules

- **Agents never apply SQL to a remote database.** Do not pass `--approve-sql`. Do not run `psql`, `supabase db push`, `supabase db reset`, or the Supabase Management API against a remote project, and do not edit `lattice.applied_sql`. If SQL needs applying, stop and tell the user to run `npm run deploy:aws -- --env <env>` themselves (in Claude Code: `! npm run deploy:aws -- --env dev`). A refusal from the SQL confirm is the expected result for an agent, not an error to work around.
- A schema change adds a feature migration and runs `npm run supabase:master` in the same change. Do not write LATEST by hand.
- Never put seed rows in a timestamped migration. The Thing demo rows live in `migrations/seed/features/things.sql`.
- Skip a seed row when its referenced id is missing. Do not fail the rest of the file. A missing table still fails the file.
- Do not rename or edit a feature migration a remote database has already applied. Add a new one.
